ExhataQ Music Player — Project Reference

This file is a standing reference to the codebase: what's where, what stage the
code is at, and what each file does (down to its exported functions). It is
not a set of job instructions — that's what Source/claude.md and AGENTS.md are
for. Read this to get oriented; read those to know how to work in this repo.

Public repository: https://github.com/ExhataQ/ExhataQ (keep it public when sharing)

PROJECT STATUS

The app is a free, local Electron music player for Windows. Source/ is the
development source; App/ is the built/runtime application (App/electron.exe).
The renderer has no bundler/module system — everything is global-scope
<script> tags loaded in a fixed order from build/music_player.html.

The 4-agent "Code Cleanup & File-Split Plan" (Source/code-cleanup-plan.md) is
complete as of 2026-09-25: all 9 oversized files it targeted have been split,
getSongById() dedup applied throughout, electron/tests/ removed, and the full
tools/tests/* suite passed at the final checkpoint (0 fail, 1 pre-existing
skip). The file lists and script-load order below already reflect that split.

Not done yet: the optional "Agent 5" code-quality pass described at the
bottom of code-cleanup-plan.md (STORAGE_KEYS centralization, a VIEWS constant,
silent-catch-block audit, DEBUG_SCAN gating for scan-folder.js logging, an
innerHTML/escaping audit, and an optional CSS-variables audit). None of its
checkpoints have been started — there's no STORAGE_KEYS object and no
DEBUG_SCAN flag anywhere in the source yet.

AUDIO FILE PROCESSING ARCHITECTURE

Source/electron/scan-folder.js (RUNTIME PHASE):
- Node.js orchestrator using the music-metadata library.
- Copied to App/*.js during build; runs as an Electron child process.
- Handles ALL audio scanning: importing dropped files, changing music
  folders, download-and-scan, rebuild-from-folders.
- No longer holds the scan logic itself — it wires together the strategy
  modules below and keeps folder-config helpers (loadMusicFolders,
  saveMusicFolders, addMusicFolder, removeMusicFolder) and shared
  utilities (walkDir, printProgress, SUPPORTED_FORMATS, the main() CLI
  dispatcher for full/rebuild-all/rebuild-all-streamed/metadata-only/
  single-file modes). Exports: sanitizeString, sanitizeLyrics,
  extractAllNativeTags, extractExtendedMetadata, scanSingleFile,
  scanMultipleFiles (the last two re-exported from single-file-rescan.js).
- Editable file ✓

Source/electron/tag-builder.js — shared tag-to-song construction, extracted
  from the 4 near-identical blocks that used to live in scan-folder.js.
  TAG_BUILD_PROFILES (INCREMENTAL/FULL/FAST/SINGLE) documents the real
  behavioral differences between the 4 scan paths (native-tag fallbacks,
  native cover fallback, sample-rate duration fallback, URL control-char
  stripping, whether covers are extracted at all, whether the covers folder
  is pre-created) instead of silently merging them. Functions:
  buildSongFromTags, buildCoverFromMetadata, generateThumbnail-related
  helpers (loadJimp, loadSharp, logThumbEngine, thumbFileNameFor,
  flattenOntoWhite, pickPicture, pickCoverExtension, writeFileAtomic,
  logCoverError), sanitizeString, sanitizeLyrics, formatDuration,
  extractAllNativeTags, extractExtendedMetadata, extractCoverFromNative.
  Sharp is the primary thumbnail engine with Jimp as fallback.

Source/electron/full-scan.js — createFullScanner({ walkDir, printProgress })
  → { scanMusicFolder }. Full re-scan of one folder, one file at a time
  (not concurrent), using TAG_BUILD_PROFILES.FULL.

Source/electron/incremental-scan.js — createIncrementalScanner({ walkDir,
  loadMusicFolders, printProgress, isSilentMode }) → { scanAllFolders }.
  The legacy incremental rebuild path: scans every configured folder
  sequentially using TAG_BUILD_PROFILES.INCREMENTAL (no native-tag/cover
  fallbacks, no sample-duration fallback — intentionally, to preserve old
  behavior).

Source/electron/fast-scan.js — createFastScanner({ walkDir, loadMusicFolders,
  printProgress }) → { scanMusicFolderStreamed, scanAllFoldersStreamed }.
  The fast/streamed path used for normal app startup and folder changes:
  a 6-worker pool does a tag-only first pass (profile FAST, no cover) and
  streams a FASTRESULT line to stdout immediately, then a second 5-worker
  pool (scanCoversConcurrently) extracts covers in the background and
  streams COVERBATCH progress lines every 25 files so the UI can patch
  covers in as they arrive.

Source/electron/single-file-rescan.js — scanSingleFile(filePath,
  coversFolder, mm) and scanMultipleFiles(filePaths, outputDir, mm), used
  for importing dropped files and single-file rescans. Uses
  TAG_BUILD_PROFILES.SINGLE (full fallbacks, covers folder created on
  demand).

Source/build/music_player.py (BUILD PHASE):
- Python script that does NOT do metadata scanning.
- Only preserves song data from the previous App/MusicPlayerOutput/player.js
  and re-injects it into regenerated output.
- Editable file ✓

Do not confuse the build-time script (music_player.py, no metadata scanning)
with the runtime scanner (scan-folder.js + its 4 strategy modules +
tag-builder.js, which do all the actual tag/cover extraction).

Source/electron/ contains:

main.js — Electron main-process orchestration and IPC registration: window
  lifecycle, app bootstrap, first-run welcome-select-folder flow, scanner
  calls, folder config operations, download folder operations, lyrics file
  IPC, online lyrics IPC, online metadata IPC, metadata editor IPC
  (get-audio-metadata, save-audio-metadata, export-audio-metadata-json,
  import-audio-metadata-json, choose-cover-image, save-audio-cover), thumbar
  wiring, close/minimize/maximize app, show-file-in-explorer, delete-file.

preload.js — contextBridge electronAPI. Exposes window controls, IPC calls
  to main, and event listeners for thumbar, window maximize, scan cover
  batch, and scan covers complete.

package.json — Minimal Electron config plus the built-in Node test script
  (npm test runs node --test ../tools/tests/*.test.js).

window-manager.js — Main BrowserWindow creation, window-state load/save,
  thumbar wiring, drag region injection, minimize-on-close handling, and
  getMainWindow accessor.

loading-window.js — Loading window creation, progress updates with circular
  SVG progress, and cleanup.

scanner.js — Shared scan-process execution and progress handling; pure JSON
  extraction and append/prepend merge functions are separated from
  filesystem/fork orchestration so they can be unit-tested without Electron.
  Downloaded scans prepend and dropped-file scans append, preserving their
  existing behavior.

music-folders.js — Music-folder configuration reading/writing plus pure
  folder validation/removal/song-count helpers. Path comparison uses
  Windows normalization; song counts require the song path to be inside the
  folder rather than merely sharing a string prefix.

downloads.js — Download-folder configuration reading/writing, target
  selection (temp vs. configured folder), remote file downloading with
  progress callbacks, filename collision handling with (n) suffixes, and
  download-folder reset.

file-operations.js — Lyrics file open/save operations using the main window
  reference from window-manager.js.

online-lyrics.js — LRCLIB API client for the Electron main process. Builds
  exact-match (/api/get) and broad-search (/api/search) requests, retries
  transient HTTP errors with backoff, de-duplicates the exact match out of
  the search results, and returns { exact, results }. Provides
  downloadLyricsFile for saving LRC or plain lyrics into the configured
  download folder with collision-safe filenames. Exposes searchLyrics and
  downloadLyricsFile.

online-metadata.js — MusicBrainz and Cover Art Archive client for the
  metadata editor. Keeps one persistent HTTPS connection, serializes
  MusicBrainz requests with a minimum interval, retries transient
  HTTP/network failures, and supports both recording and release scopes.
  Cover-art redirects are only followed to trusted MusicBrainz/Cover Art
  Archive/archive.org hosts, capped in count and response size; image type
  is sniffed from the actual bytes rather than trusting Content-Type; a
  cover result is reported as downloaded / none / failed(reason). Downloads
  covers to a userData metadata-cache folder. Exposes searchOnlineMetadata
  and getOnlineMetadata. USER_AGENT still has a placeholder contact email
  that needs replacing before heavy day-to-day use against the real API.

metadata-editor.js — Node wrapper that spawns metadata-editor.py with a JSON
  request over stdin, tries python then py -3 (or python3 then python on
  non-Windows), parses the Python process's JSON response, and converts
  file URLs to filesystem paths. Exposes getAudioMetadata, saveAudioMetadata,
  saveAudioCover.

metadata-editor.py — Python/mutagen backend for reading and writing common
  audio tags and embedded covers. Reads ID3 (MP3), Vorbis/FLAC, MP4/M4A, and
  ASF tags into a normalized metadata object, exposes extra tags in an
  otherTags array, and writes text, multi-value, track/disc, comment, sort,
  MusicBrainz, and cover fields as native frames for the destination format.
  Standard ID3 sort-frame writes go through the shared set_text/set_multi/
  set_txxx helper; ID3_UNSUPPORTED is kept as a documented extension point.
  Sort Composer now actually saves for MP3 (TSOC). Lyricist (TEXT) and
  Writer (TXXX:WRITER) no longer share a frame; TOLY is still read as a
  legacy fallback but no longer written. Known gap: FLAC/OGG still silently
  no-op on Lyricist, Writer, Producer, Description, Mood, Language, Media
  Kind, and MusicBrainz Release Group Id (Vorbis-comment support was never
  implemented for those fields).

Electron main-process structure: main.js owns IPC registration and
application bootstrap, including the first-run welcome-select-folder flow,
online-lyrics IPC, online-metadata IPC, and metadata-editor IPC;
window-manager.js owns the main window and window-state persistence;
loading-window.js owns the scan/loading progress window; scanner.js owns
shared scan-process execution, progress handling, result parsing, and
scan-result merging; music-folders.js owns music-folder configuration and
folder metadata operations; downloads.js owns download-folder configuration
and remote file downloading, delegating the downloaded file to scanner.js
for scanning and merging; file-operations.js owns lyrics file dialog and
filesystem operations; online-lyrics.js owns the LRCLIB client;
online-metadata.js owns the MusicBrainz/Cover Art Archive client;
metadata-editor.js spawns the Python mutagen backend and metadata-editor.py
performs the actual tag reads/writes. scan-folder.js is the thin runtime
orchestrator over full-scan.js / incremental-scan.js / fast-scan.js /
single-file-rescan.js, all of which build songs through the shared
tag-builder.js.

Note: fonts are self-healing. Source fonts live in Source/tools/fonts/ and
are copied to App/MusicPlayerOutput/fonts/ on every build. If any font file
is missing from both, music_player.py downloads them from CDN. all.min.css
paths are rewritten from url(../webfonts/...) to url(...) after download.
